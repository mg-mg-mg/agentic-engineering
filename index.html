1. Owner attention is the scarcest resource

The repo contract (AGENTS.md, ~63 KB plus nested rules and task skills) makes decision rights explicit. An agent that stops to ask for a decision it could make costs more than a reversible mistake it catches and fixes.

DecisionWho
Technical design, root-cause scope, refactoring, slicing, test strategy, task orderAgent decides and reports why
Defects found while working, tooling recovery, Issues, branches, worktrees, PRs, docs and rule updatesAgent acts then records
Deployment, store submission, payments, production data, external messages, spending, credentialsOwner approves asked once, with a recommendation
Product direction, pricing, user-facing policy, final Korean copyOwner decides agents keep working meanwhile

2. The system

Three kinds of agent lanes feed one GitHub queue, and everything passes the same gates.

Ownerproduct, priorities, irreversible approvals

Interactive lead sessions

  • One long-lived lead per workstream: deploy, lead, refactor, payments, ops/marketing
  • Lead owns design, integration, final verification
  • Delegates bounded slices to workers in isolated git worktrees, one owner per generated surface

Unattended Issue pool

  • 4 macOS LaunchAgent workers, 180 s tick
  • Each claims one unowned P1/P2 bug or maintenance Issue
  • Author, reviewer, verifier are separate processes with separate permissions (below)

Browser agent (QA / ops)

  • Live E2E: payment checkout, refund, cancel in test mode
  • 7-locale i18n/UX audits, dashboard audits
  • Files Issues to coding lanes via a repo mailbox and the harness debug socket

3. One unattended Issue, end to end

The author can write code but cannot reach the network; the only process with credentials is the dispatcher, and only for the write it is about to make.

ClaimWorker picks one unowned P1/P2 Issue from a full Project/PR/dependency snapshot.excludes payments, holds, owned work
AuthorImplements and runs local checks in an offline worktree sandbox.no network, no secrets, no git push
DispatcherValidates Issue state, reviews the diff, publishes the PR, verifies the remote head.only process with GitHub write
ReviewerSeparate read-only model reviews fixed head/base SHAs against acceptance criteria.read-only
VerifierSeparate credentialless process reruns the chosen checks; must not change the head.no credentials
Guarded mergeIntent saved, squash merge pinned to reviewed head, parent/tree verified, evidence posted.then Issue/Project reconciled
Findings or failed checks go back to the same author lane. Every revision needs a new head, a fresh review, and passing verification, until mergeable or a 5-hour budget expires.
Never unattended: deployments, app-store submissions, production data writes, payments, credential changes, external messages.

4. What I learned

1

Throughput is cheap; trust is expensive.The bottleneck moved from writing code to acceptance criteria and gates that make agent output trustworthy without reading every line.

2

Separate the roles.A model reviewing its own work misses the same things. Separate author, reviewer, and verifier processes catch far more.

3

Least privilege for agents.Authors need no network and no secrets. Credentials live only where a specific write happens.

4

Write the rules where agents read them.Decision rights and workflows live in versioned repo docs, so every session starts from the same contract and rules improve through PRs.

5

Find errors before runtime.Typed contracts and generated clients turn agent mistakes into build failures instead of production incidents.

6

Spend human attention on the irreversible.I approve deploys, payments, pricing, and policy. Almost everything else is delegated and audited.
